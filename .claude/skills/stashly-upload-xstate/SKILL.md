# Stashly Upload Architecture (XState)

The upload system uses a parent-child actor pattern:
- `upload/upload.machine.ts` — parent, spawns one `file.machine` per file, manages the queue
- `reviset/file.machine.ts` — active upload actor: creates multipart upload, uploads chunks in parallel, verifies ETags
- `quota/quota.actors.ts` — `checkQuota`, invoked by `reviset/file.machine.ts` as the pre-upload gate. The neighbouring `quota/quota.machine.ts` is **not spawned**: until 2026-10-26 the parent spawned it into `quotaActor`, where it sat in `idle` because nothing ever sent it an event. It is kept, unimported, in case quota reads move into one shared actor; it neither tracks nor enforces anything.

**Quota is charged on the server, in `createUploadedItem`, nowhere else, to the folder's drive**: the charge (`stashly_charge_upload()`, migration `20261106120000_upload_quota_log`) is part of the one statement that creates the `Item` (`insertUploadedItem`), so the row and the charge commit together or not at all (a drive with no `Quota` row gets no row). The drive is the parent's, never the session's: a collaborator's upload charges the folder's owner, the row takes that `driveId`, and refunds follow it. `Item.ownerId` stays the uploader and the bytes stay in the uploader's bucket. Far from the limit a busy upload logs its charge in `QuotaDelta` and the rollup adds it; near the limit it takes the drive's advisory lock exclusively and charges through a strict check, one at a time. The pre-check (`/api/quota` with `folderId`, `findQuotaForFolder`) answers for the same drive, only ever yes or no, and a refused collaborator isn't told the owner's free space. No client code charges quota: `dbMachine` has no quota state, and `/api/quota` is read-only — `items-uploaded` and the other write actions answer 400. Do not add a client-side charge back. History: until 2026-09-27 both the file machine and `createUploadedItem` charged (twice per upload); `c6751b2` then kept a client charge in `dbMachine` (`chargingQuota`/`retryingQuota`), which a client could skip or forge; 2026-10-08 moved it back into the transaction. Test fixtures that call `createUploadedItem` need a `Quota` row on the folder's drive, and read `used` after `flushItemSizes()` (see `upload-quota-charge.test.ts`).

**The size charged is the stored object's, never the form's.** `create_upload_item` reads the object with `headUploadedObject(user.bucket, key)` (`app/.server/s3.ts`) before `createUploadedItem`, and passes its `ContentLength` and ETag on; the form's `size` and `etag` are only the client's claim, compared and logged (`upload claim differs from the stored object`) when they differ. Until 2026-10-31 the form's size was charged, so a scripted client claiming 0 stored any file for free (measured: three 10 MB files filed at size 0, quota unmoved). The HEAD runs **before** the `try` whose refusal calls `discardUploadedObject`: no row serves the object yet, so a missing object (looked for twice, 250 ms apart) or a storage error answers `{ success: false, error }` and keeps the bytes for the orphan sweep. It adds about 90 ms to `create_upload_item` (186–230 → 294–323 ms, 3 runs each); a probe of 223 complete-then-HEAD cycles on Tigris found no object missing and no size or ETag mismatch. Tests: `items-invalid-input.test.ts`, `upload-item-safety.test.ts`.

**The charge is also the quota enforcement.** The `UPDATE` only matches when `used + size <= total`; otherwise the statement inserts nothing, `refuseUploadedItem` throws 507 `INSUFFICIENT_QUOTA`, and `/api/items` discards the bytes. The check sits in the `UPDATE`'s own `WHERE`, so two concurrent uploads can't both take the last free space. The file machine's `checkingQuota` is only a pre-check that saves the transfer: a `denied` answer goes to `error` (status `failed`, reason "Not enough storage…") before any multipart upload starts. Its guard reads the done **event**, not context — a transition's guard runs before its actions assign. Until 2026-10-10 the guard was commented out and the result stored by a plain (non-`assign`) action, so a denied file uploaded and was charged past its total. Tests: `upload-quota-charge.test.ts` (refusal, exact fill, concurrency), `reviset/__tests__/file-quota-check.test.ts`.

Concurrency is gated **inside `upload.machine.ts` itself** via `maxConcurrentUploads` (default 100, see `schemas/machine.schemas.ts`) — there is no separate queue actor in the live path.

> The old queue, quota and multipart prototypes (`actors/*.machine.ts`, `queue/`, `reviset/queue.machine.ts`) and the `upload/file.machine.ts` sibling are deleted; `app/machines/actors/` holds only a shared `types.ts`. Don't recreate a queue actor: the manager owns concurrency.

Files upload via S3 multipart: frontend → `/api/s3/upload` → uploads directly to S3 bucket. **The `/api/s3/upload` route uses JSON body (`request.json()`) with an `action` discriminator — not form-encoded.**

**Upload calls to our own server go at `priority: 'low'`**: the `FetchInit` in `s3.mulipart.utils.ts` (create, sign, complete, abort), the part-URL windows in `s3.multipart.stream.ts`, and `postItem` in `db.actors.ts`. Over HTTP/1.1 (dev) Chrome sends six requests at a time per origin; at default (`high`) priority these filled all six and kept `save_media_metadata` waiting ~7 s per request against ~15 ms on the server, so facets landed after the upload and a reload lost them (tech-debt item 53). Measured on a 660-file upload: metadata saves by the last row 49 → 630, and the upload no slower. A new upload-time call to our origin takes `low` too. Part PUTs go to S3, a different origin, and keep the default.

**Item creation runs in its own machine**: `machines/db/db.machine.ts`, spawned per file by `triggerItemCreation` on `upload.done`. It never throws — a spawned actor's unhandled rejection **stops the parent**, which is how one failed file used to cost a whole batch its rows. It answers `upload.createItem.success` or `upload.createItem.error` on every path. A failure sets status **`itemFailed`**, not `done`: the bytes are in S3 but the row is not, and the panel renders it as "failed" with the reason in a tooltip. Note `POST /api/items` answers an expired session with `throw redirect('/auth/sign-in')` and `fetch` follows redirects, so the client sees a **200 carrying HTML** — `postItem` reads the body as text and `toOutcome` classifies it, rather than letting `res.json()` throw.

**Item creation gate**: The thumbnail pipeline and `POST /api/items` must NOT fire on `status === 'done'` (S3 done, but DB row not yet written). Wait for `status === 'itemCreated'` — set by `markAsItemCreated` action in `upload.machine.ts` after `upload.createItem.success`. Firing on `'done'` causes FK violations on `Thumbnail.itemId`.

**Two strings per upload, built in `toMediaFile`** (since 2026-11-01): `uploadPath` is `<rootId>/<folders>/<name>`, where the file goes, and `key` is the object's own S3 key, `toObjectKey(uploadPath, id)` = `<rootId>/<itemId>/<name>`. Until then the key *was* the path, so two uploads of one name shared one object: the second replaced the first's bytes, a copy's bytes went with it, and the duplicates triage compared one object with itself. Unique keys are what versions and that comparison need, and Tigris has no bucket versioning (`PutBucketVersioning` unsupported) to fall back on. `File.uploadPath` stores the path as a record of the upload; it is **not** the file's current place (a move leaves it as it was), which the folder tree gives. The file machine only hands `key` to S3 and never parses it. `createUploadedItem` refuses (400) a key that is not `toObjectKey(uploadPath, id)`.

**`parentId` derivation**: the first segment of the upload path is the destination root, the middle segments are the folder path, and the last is the filename. A folder upload (`addBatch` in `useUpload.ts`) resolves its whole folder tree **once**, before its files start: one `resolve_upload_folders` request (`/api/items`) → `resolveUploadFolders` → `resolveFolderTree` (`.server/item-actions.ts`), which finds or creates every folder with one query per depth level and one INSERT for all missing folders, under **one advisory lock per uploader** (`folder-tree:<ownerId>`), held only while the tree resolves. Each file then carries its leaf folder as `mediaFile.parentId` (in the `mediafile` schema, so `mediafile.parse` keeps it), and `toItemPayload` posts it. The server treats it as the client's word: `createUploadedItem` checks `write` access on it, and the insert itself only runs while it is a live folder. A file with no resolved parent (single-file `add`, a refused path, a failed resolve) posts segment 0 and `createUploadedItem` resolves its key path as a batch of one, the same way. Measured 2026-10-25 on a 639-file / 71-folder `app/` upload: 11,600 statements, 1,278 transactions and 1,824 locks before; 1,284, 1 and 1 after.

**`addBatch` must hand files over one at a time.** Each file is sent after its own `await normalizeFile(file)` (a disk read for `.ts`/`.tsx`), which lets the machine start the uploads already queued. Queuing all 639 in one synchronous burst (normalize all, then send all) started 100 uploads at once, and the upload took 872 s instead of 707 s. Keep the resolve request before the loop and the loop itself unchanged.

**The file row is one statement.** `insertUploadedItem` writes `Item`, `File`, `Permission`, the `_PermissionToUser` link and the quota charge (`stashly_charge_upload()`) as a single data-modifying CTE: no transaction, and each step reads from the one before, so a missing or trashed parent, a file that doesn't fit or no quota writes nothing and charges nothing. The `parent` read is `FOR KEY SHARE`, the lock the `parentId` foreign key takes anyway. That keeps its status check from going stale against a trash running at the same moment, which holds its folders `FOR UPDATE` (tech-debt item 66). Size and child-count updates don't conflict with it. `resolveFolderTree` holds the root and every folder it finds the same way until it commits, but only once the tree is known: its lookups take no lock, then **one statement locks the root and all found folders in id order** and re-reads them, answering 404 when any is trashed. Locking a level at a time deadlocked with a trash of the root whenever a subfolder's id sorted before the root's (`40P01`, tech-debt item 72). Only after a refusal does `refuseUploadedItem` run one more query to say why (404 / 507 / `QUOTA_NOT_FOUND`). `$queryRaw` is invisible to `tsc`: a new column on those tables needs adding there, and `upload-folder-tree.test.ts` (live DB) guards the behaviour, including that the write is 2 statements after resolution. While the database is busy (another upload cascading, a rollup running, or deltas pending), the folders above the file are **not** in that statement: `update_size()` logs its size, and `app/.server/size-rollup.ts` (started when `server/app.ts` loads, so at boot in production) applies it within about 250 ms, so 32 uploaders into one shared folder no longer queue on its ancestor rows. The folder's child count and the quota charge take the same log, so they no longer queue on the `Folder` and `Quota` rows either (32 uploaders, one drive: 547 → about 2,150 files/s, 29 → 0.05 of 32 waiting on a lock). While idle the statement writes all of them at once, as before.

**Access is checked before any bytes move.** `assertCanUploadTo(userId, key)` (`write` on segment 0) runs in `/api/s3/upload` at `create-multipart-upload` and again at `complete-multipart-upload`, where a refusal aborts the multipart upload so S3 drops the parts. A refusal answers `{ error }` with its status; `readUploadResponse` in `s3.mulipart.utils.ts` throws that text. Part signing is not checked. **So is the key:** `assertKeyUnfiled(bucket, key)` refuses with 409 at both steps when a `File` row (trashed included) already serves the key. An honest client never trips it, since every key is new; it stops a scripted client from uploading over a filed object, which swapped the bytes behind the row while its size and the quota kept the old number. Same-name uploads are fine: each is its own item and object. The lookup uses the `file_bucket_key` index. Tests: `upload-abort.test.ts`, `upload-item-safety.test.ts`.

**Part URLs are signed a window at a time.** `create-multipart-upload` takes `partCount` (the file machine sends `partCountFor(file.size)`) and returns the first 100 URLs as `partUrls`; the file machine keeps them in context and hands them to `uploadParts`. Beyond 100 parts, `createPartUrls` in `s3.multipart.stream.ts` asks `get-presigned-urls { from, count ≤ 100 }` 20 parts ahead of need, one request per window shared by the workers. A part PUT answering 403 is re-signed once, since Tigris answers an expired URL with 403 `AccessDenied` "Request has expired" (probed 2026-10-26); a second 403 fails the file. The per-part `get-presigned-url` action stays, but the live path no longer calls it. Measured 2026-10-26: a 100 MB upload makes 10 requests to our server, not 30. Tests: `multipart/__tests__/part-urls.test.ts`, `routes/api/__tests__/upload-presign.test.ts`, `reviset/__tests__/file-part-urls.test.ts`.

**A file that fails before its bytes are stored reports it.** The file machine's `error` state (quota check, create or complete failed) sends `upload.failed { mediaFile, error }`. The manager marks the file **`failed`** (distinct from `itemFailed`: no bytes stay in S3), keeps the reason on `error`, frees its slot and starts the next pending file. Before this the file held its `queues.active` slot for good, and after `maxConcurrentUploads` failures nothing else could start. The panel shows both failure statuses as "failed" in the same colour as every other status, with the reason in a tooltip. Test: `app/machines/upload/__tests__/upload-failed.test.ts`.

**A cancelled or failed transfer aborts its multipart upload.** A user cancel and running out of part retries both pass through the file machine's `abortingUpload` state, which runs `abortUpload` (deliberately unsignalled, so it outlives the machine) and then reaches `aborted` whether or not it succeeded. Tigris rejects an `AbortIncompleteMultipartUpload` lifecycle rule, so without this the parts stay billed until the hand-run orphan sweep. A failed `complete-multipart-upload` aborts too, through `abortingFailedUpload`, then ends in `error` with its reason; the route answers an already-aborted upload (`NoSuchUpload`, as after a refused complete) as done. `retryFetch` in `s3.multipart.stream.ts` retries only 429, 5xx and network errors: any other 4xx fails on the first answer, so a share revoked mid-upload fails the file at once instead of after minutes of backoff. Tests: `reviset/__tests__/file-abort-multipart.test.ts`, `multipart/__tests__/retry-fetch.test.ts`, `routes/api/__tests__/upload-abort.test.ts`.

**Filing never guesses, and a refusal cleans up.** `createUploadedItem` requires `write` access to segment 0 as the *session* user (the route ignores the form's `ownerId`). On the path, a trashed folder never matches, and two live folders with the same name refuse the file with a 409 that says which name and where, instead of picking one. When the row can't be created, the route calls `discardUploadedObject`, which deletes the bytes only if no `File` row points at them, and only in the user's own bucket (read from their row; the `default-bucket` placeholder counts as none). It does not require folder access, so a revoke mid-upload still cleans up. The route also files with the session's bucket, not the form's. Nothing retries a refused row, so without it the object stays in S3 for good. Tests: `app/.server/__tests__/upload-item-safety.test.ts`.

Directory drops keep their hierarchy through `webkitRelativePath`, which becomes the upload path (`utils/converters.ts`) and the folders `resolve_upload_folders` creates. **The browser fills it only for `<input webkitdirectory>`**: a file from a drag-and-drop (`FileSystemFileEntry.file()`) always reads `''`, and the path lives on the entry's `fullPath`. `collectFiles` in `useUpload.ts` copies it over with `withEntryPath` (test: `hooks/__tests__/useUpload.test.ts`). Until 2026-11-09 it didn't, so every dropped folder, on any drop target, was filed as loose files in the destination. `normalizeFile` (`utils/sniff.ts`) re-sets the property on the files it rebuilds, so it survives that step too.

**A freed slot goes only to a file without one.** A file keeps status `pending` until its multipart create returns, while it already holds a slot, so `uploadPendingFiles` skips files in `queues.active`. Before 2026-11-09 it didn't: those files came first (added earlier), `upload.start` refused them as already active, and the slot went unused, so a large drop ran ever further below `maxConcurrentUploads` (seen as ~10 uploading of 100). Test: `upload-concurrency-limit.test.ts`, kept in a file whose other tests add no files, because the manager's initial context is one module-level object its actions mutate.

**New rows reach the page without a reload** (tech-debt item 45, 2026-11-01). `create_upload_item` answers `{ success, item }` with the item's folder-listing row (`getCardItems`, `folderCardSelect`, sent through `cardItemOutput`), and `resolve_upload_folders` adds `created`, the rows of the folders it made. The row rides `@db.item.created` → `upload.createItem.success { item }`; the manager **emits** `items.created` (also for `upload.items.created`, which `addBatch` sends with the folders) and keeps nothing in context. `useCreatedItems` (`useUpload.ts`) revives the rows (`reviveCardItem`: BigInt sizes, Dates) and hands them to `usePagination.insertItems`, which places them with `showCreatedRows` and returns the ids it showed for certain. When the batch ends (no file in flight or `done`), `upload-thumbnail-runner.tsx` takes those ids (`takeShownRows`) and does one `navigate(…, { replace: true, state: { reset: true } })` only if a created row is missing. No other upload-time folder reload exists; the indexing `revalidate()` runs only on facet routes. Before this, a 700 ms debounce on the created count reloaded the folder after almost every row whenever rows arrived more than 700 ms apart (14 reloads for 30 files; 0 now). A failed card read answers with no `item`, never a partial row: a partial card crashed the favorite action.

## AI Machines

There is no `app/machines/ai/` any more: its two unwired experiments (`ai.machine.ts`, `caption.machine.ts`) were deleted in `9133214`. The running pipeline is `machines/pipeline/` plus the workers in `app/workers/` (all inference funnels through `ai-queue.ts`). Check the importers before assuming a machine under `app/machines/` is wired up.

AI API routes live under the `/api/ai/` prefix (see `app/routes.ts`).
